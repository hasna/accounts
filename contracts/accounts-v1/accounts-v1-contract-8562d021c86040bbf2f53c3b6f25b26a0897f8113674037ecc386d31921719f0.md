# Accounts V1 capacity contract

Status: proposed contract and implementation gate, 2026-07-10.

This document freezes the Phase-0 contract for the clean Accounts package,
implemented in Phase 1 and integrated with Infinity in Phase 2. It is limited
to the Hasna deployment modes local and self_hosted. It is not a multi-tenant
SaaS contract. The words MUST, MUST NOT, SHOULD, and MAY are normative.

## Decision

Keep the Accounts domain and package ownership, but build the durable capacity
catalog as a structurally isolated workspace/build. The existing local profile
switcher is migration evidence, not a runtime donor. The only permitted V1
reuse is a quarantined, metadata-only importer.

Accounts V1 owns:

- provider-account, entitlement, lane, and AuthCapsule metadata;
- non-secret credential bindings by opaque reference;
- capsule placement, isolation-attestation, refresh, health, and terms metadata;
- signed, short-lived, non-reservational SlotEligibility evidence;
- the same domain semantics in local SQLite and self-hosted Postgres.

Accounts V1 does not own:

- raw credentials or provider session material;
- run admission, scheduling, lane selection, fairness, budgets, attempt-lease
  issuance for a run, retry, cancellation, or terminal state;
- task execution, repository checkout, shell execution, model routing, or
  sandbox cleanup.

The first implementation gate is therefore a conditional GO for the catalog,
storage, CLI, and SDK. It is a NO-GO for unattended provider access through
either a native AuthCapsule or a brokered lane until the separate containment,
provider-terms, credential-broker, and stale-lease tests pass.

The published package is useful compatibility code, but it is not the capacity
contract required by Infinity:

- Profile is path-oriented and has no typed ProviderAccount, Entitlement,
  AccountLane, AuthCapsule, CredentialBinding, terms decision, placement,
  refresh owner, isolation attestation, or fence.
- Tool definitions can carry arbitrary launch arguments, environment values,
  and dangerous permission presets. The package can launch child processes with
  inherited environment and can copy Claude credential state between files and
  the macOS keychain.
- The registry contains no raw credential, but the package itself manages raw
  credential snapshots. That makes the existing profile runtime unsuitable as
  an Infinity security boundary.
- Local JSON and self-hosted Postgres do not implement one storage contract.

  historical S3 meanings.
- There is no single published/default-branch/installed version to treat as a
  trustworthy migration base.

Consequently, the existing Profile API MUST NOT be relabeled, linked, or
imported as the new Accounts V1 domain. It may remain temporarily available in
its quarantined legacy deployment during an explicit consumer cutover, but it
is not a compatibility surface inside V1.

## Deployment contract

Deployment mode is explicit and has exactly two values:

| Mode | Authority and transport |
| --- | --- |
| local | One operator, in-process SDK/CLI, SQLite at ~/.hasna/accounts/accounts.db |
| self_hosted | Hasna-owned AWS service, authenticated HTTP API, RDS Postgres |

There is no cloud mode, remote mode, hybrid mode, automatic mode, S3 mode, or
automatic fallback. The environment selector is
HASNA_ACCOUNTS_DEPLOYMENT=local or self_hosted.

Local and self_hosted databases are independent authorities. Changing mode MUST
NOT silently copy, merge, cache, or reconcile records. A transfer is an
explicit, dry-runnable, checksummed export/import operation containing metadata
and non-sensitive binding descriptors only. It excludes credentialHandle,
vault/path/role locators, local-state identifiers, SlotEligibility evidence,
attestations, and broker denial state. Imported binding descriptors exist only
as non-authoritative import_candidates, never as pending/unbound
CredentialBinding rows, and require owner re-verification plus an atomically issuer-minted
credentialFamilyId/handle before a real pending binding exists. Exported
capacity-pool descriptors likewise remain import_candidates, not CapacityPool
rows; a fresh provider-capacity verifier transaction either deduplicates them
to an existing pool or creates the first real pool from new-installation
evidence. Old-install domain/family ids and evidence never enter authoritative
columns. Credential material is never part of an export.

Capsule placement is a different axis from Accounts deployment:

- enrolled_node means an owner-controlled, Machines-enrolled trusted node.

V1 AuthCapsule placement is enrolled_node only. A future trusted AWS cell needs
a separately reviewed discriminated placement variant (cell/workload identity,
non-exportable key confirmation, cell generation, and measurement); mixed node/
cell fields are rejected. Self-hosted Accounts deployment does not imply
self-hosted capsule placement.

A capsule MUST NOT be placed in the Infinity control account or in an untrusted
task workload account. The term remote describes location only and is not
accepted as a deployment-mode value.

### No-SaaS enforcement

No-SaaS is enforced in code and schema:

- A singleton installation record fixes deploymentMode to local or self_hosted
  and fixes identityRealm/organizationRef to the configured Hasna realm. These
  values are deployment-owned, not request fields.
- Tables have ownerRef but no tenantId, customer organization, public plan,
  signup, invite, metering-for-resale, or SaaS billing dimension.
- Write schemas use additionalProperties=false and reject tenantId,
  organizationId, deploymentMode=cloud, outside-realm owner refs, and
  caller-selected auth issuer/audience.
- Self-hosted authentication accepts only configured Hasna issuers and the
  capacity-service audience; routes have private internal ingress, no anonymous
  registration, no wildcard CORS, and no outside-user credential issuance.
- The OpenAPI document contains no tenant/signup/invite/public-key route.
  Local mode is in-process or owner-only local IPC; self_hosted is private
  Hasna infrastructure.

Conformance tests inspect the schema/OpenAPI and exercise rejected outside-realm
issuers and fields. Adding a tenant/customer/public-registration dimension is a
new product and security review, not an additive V1 option.

## Authority boundaries and runtime flow

~~~text
authorized human or service
    -> Accounts: catalog and policy metadata
       -> ProviderAccount -> Entitlement -> AccountLane
          -> native AuthCapsule -> capsule-local CredentialBinding
          -> or lane-level brokered CredentialBinding

Infinity Run Authority
    -> issues an attempt lease for a run with a monotonically increasing lease epoch
       -> validates Accounts SlotEligibility
          -> atomically serializes the account slot in resource_leases
             -> broker validates live Infinity lease/capability
                -> online Accounts generation/deny recheck
                   -> trusted capsule or credential broker
                      -> Secrets/workload broker or capsule-local native store
                         -> provider-native channel

isolated task sandbox
    -> narrow tool RPC only
    -> never receives provider/session/API credentials
~~~

The Infinity Run Authority is the only production issuer of both attempt
leases for runs and account-slot resource leases. Accounts signs SlotEligibility with a
stable serializationKey, maxConcurrency, exact access-target/credential
generations, expiry, and current deny generation. That evidence neither
reserves nor authorizes capacity. Infinity atomically serializes the account slot in its own
resource_leases table. Accounts' monotonic deny/revocation generation can
invalidate account access but cannot change Infinity run state.

Secrets/workload-identity broker and an attested capsule-local native store are
the only credential-material resolution boundaries. SandboxRunner is the only
task execution authority. Any design that gives Accounts an AccountSlotGrant,
independent account lease, account_lease_id, LaneFence, or run authority is
incompatible with this contract.

## Domain model

All IDs are opaque UUIDv7 values generated by the domain layer. Natural names
are labels, never primary keys. Every mutable aggregate has revision, createdAt,
updatedAt, and an append-only audit event. Mutations use expectedRevision and an
idempotency key.

Cardinality is ProviderAccount 1:N Entitlement and 1:N CapacityPool;
Entitlement 1:N AccountLane; every lane references one CapacityPool belonging
to the same ProviderAccount. A native_session capacity domain has at most one
non-revoked AuthCapsule installation-wide and that capsule has native credential
bindings. api_key and workload_identity lanes have lane-level brokered
CredentialBindings and MUST NOT create an AuthCapsule.

### ProviderAccount

A provider account is an owner-bound relationship with a provider.

Common fields are id, providerKey (stable adapter key such as openai,
anthropic, or aws), ownerRef (stable OpenIdentities principal), displayLabel,
status (pending, active, suspended, or revoked), revision, and timestamps.
providerDisplayHint, adapterSchemaVersion, and bounded adapterMetadata are
optional and non-authoritative. The state-dependent shape is closed:

- pending may omit providerSubjectRef or hold only an explicitly
  non-authoritative candidate fingerprint; it has no positive ownership
  evidence fields.
- active requires providerSubjectRef plus ownershipEvidenceRef, issuer/version,
  digest, issuedAt, expiresAt, and ownershipGeneration from the configured
  provider-ownership verifier. The signed evidence binds exact providerKey,
  providerSubjectRef, ownerRef, installation identity realm, and audience.
- suspended and revoked retain the last evidence for audit but are ineligible;
  a never-activated row does not invent it.

providerSubjectRef is a provider account identifier or opaque fingerprint,
never an access token, session token, email password, or cookie, and it is
redacted for normal readers. Once active, providerKey, ownerRef, and
providerSubjectRef are immutable. Activation first conditionally appends, then
transactionally mirrors, an immutable installation-wide provider-subject claim
keyed by (providerKey, providerSubjectRef), bound to exactly one ownerRef and
ProviderAccount lineage for all time. A stranded external append is
conservatively reserved, never reusable. The claim survives suspension,
revocation, retention purge, restore, and import and is never deleted or
reassigned. Pending candidate fingerprints are non-authoritative and cannot
reserve a claim. A
ProviderAccount used by a subscription-funded entitlement MUST have a human
ownerRef. A service-owned metered/IAM entitlement MAY use a service-principal
ownerRef. Revoked is terminal.

Active status alone is insufficient: ownership evidence must remain fresh and
unrevoked at every eligibility issuance and online generation check. Expiry is
detected using database time; the first scheduled/evaluation/check transaction
at or after expiry, or ingestion of verifier revocation, a higher
ownershipGeneration, reassignment, owner/subject/realm mismatch, or issuer
revocation, atomically suspends/revokes the ProviderAccount, advances its
revision, and advances the deny barrier for every child CapacityPool before
returning or issuing more evidence. The request already fails closed even if
that persistence transaction cannot commit. Verifier unavailability at an
online check fails closed.

V1 has no ownership transfer, live or after terminal revocation, for the same
providerSubjectRef or capacityDomainRef. Their immutable ownership and
installation-wide tombstones permanently prevent reparenting or a second
serializationKey. A different owner may onboard only a separately verified
provider subject and separately verified capacity domain using new records,
handles, and capsule/broker state after any relevant deny/revoke cleanup. Same-
subject/domain successor lineage is a future separately reviewed protocol; an
administrator cannot emulate it by rewrite, import, purge, or recreate.

### Entitlement

An entitlement describes what the owner is permitted and funded to use.

Common fields are id, providerAccountId, fundingKind (subscription, metered,
credit, contract, or externally_managed), status (pending, active, paused,
expired, or revoked), revision, and timestamps. The state-dependent shape is
closed:

- pending forbids positive capabilitySet, dataPolicy, and execution-policy
  fields. termsDecision may be absent, a typed unknown with reason code and no
  fabricated evidence/timestamp, or a signed denial; owner/catalog input cannot
  add positive evidence.
- active requires capabilitySet, an unexpired signed allowed termsDecision,
  typed dataPolicy, executionPolicyEvidenceRef, executionPolicyDigest, policy
  expiry, and lastVerifiedAt, all from their configured authorities.
- paused, expired, and revoked may retain the last signed evidence for immutable
  audit but are ineligible; a row that never activated does not invent it.

An allowed or denied termsDecision contains decision, useCase, evidenceRef,
verifiedBy, verifiedAt, expiresAt, and the reviewed terms version/digest. A
typed unknown contains only decision, useCase, and reasonCode. Unknown, denied,
missing, or expired decisions fail closed for unattended use; sentinel evidence
ids or timestamps are invalid.

dataPolicy is a typed allowlist of data classifications and retention
constraints. Provider-specific facts may be stored in bounded adapterMetadata,
but metadata MUST NOT grant capabilities, widen data policy, or override a typed
denial.

capabilitySet and dataPolicy are normalized projections of a signed, versioned
execution-policy decision from the deployment-configured execution-policy
authority. That decision binds the exact provider account/owner, entitlement,
use case, provider/adapter version, allowed model/operation set, data
classifications and retention constraints, required isolation-policy ref and
digest, policy version, issuedAt, and expiresAt. An owner/catalog writer may
request a stricter intersection but cannot choose, add to, or widen the
authority's values. A generic writer or administrator cannot author positive
policy evidence.

Quota and provider-cost observations include source and observedAt. They are
advisory. Infinity owns authoritative run-budget consumption.

### CapacityPool

A CapacityPool is the real provider-side concurrency/quota domain shared across
sibling entitlements, lanes, handles, and capsule replacements. Required
fields:

- id and providerAccountId
- issuer-signed capacityDomainRef and evidenceRef
- stable serializationKey and maxConcurrency
- status: pending, active, draining, denied, or retired
- capacityGeneration, denyGeneration, and denyState
- revision and timestamps

The tuple providerKey plus capacityDomainRef is unique installation-wide.
capacityDomainRef is not caller-selected; the configured provider-capacity
verifier derives it from actual upstream account/quota evidence and separately
checks broker/capsule credential-family proof. A broker/capsule issuer cannot
self-grant a distinct domain or larger limit. serializationKey is an immutable
Accounts-generated key for that pool. Every sibling entitlement, lane,
credentialFamilyId, re-minted handle, and successor capsule resolving to the
same upstream capacity MUST reference the same pool/key. Independently
evidenced provider capacity gets a distinct pool.

Before pool creation, the verifier conditionally appends the exact
(providerKey, capacityDomainRef, serializationKey, ownerRef) lineage to the
external recovery ledger. A conflict returns the already claimed lineage; a
stranded append remains denied until reconciled. The database unique constraint
mirrors this claim but is not its restore-resistant source.

providerAccountId, capacityDomainRef, and serializationKey are immutable.
Ordinary accounts:write callers cannot create/choose a capacity domain, set
maxConcurrency, or activate a pool; only verified capacity evidence can do so.
A real pending CapacityPool is created only by the configured verifier with a
current signed evidence_type=provider_capacity envelope from issuer_class=
provider_capacity_verifier that binds capacityDomainRef/evidenceRef; pending
means not yet eligible, not unverified caller data. Imports and owner
suggestions remain separate non-authoritative import_candidates and cannot
reserve a serializationKey.

provider_capacity is a closed authority-evidence payload containing exactly
provider_account_id, provider_key, owner_ref, capacity_domain_ref,
serialization_key, max_concurrency, decision, and policy_version. Its generic
signed envelope has schema_version with the sole V1 literal
accounts.authority-evidence.v1 and additionally binds evidence_type with the
literal provider_capacity, evidence_ref, subject_ref=CapacityPool id,
aggregate_kind=capacity_pool, aggregate_id, aggregate_revision,
identity_realm, issuer_ref, issuer_class=provider_capacity_verifier,
issuer_incarnation, audience, key_id, issued_at, expires_at, nonce,
evidence_generation, payload_digest, and signature. Positive creation or
eligibility requires decision=allowed; exact equality with the current
ProviderAccount/CapacityPool owner, provider, domain, serialization key, and
limit; the current non-revoked trust root/incarnation/key; and the highest
accepted evidence_generation for that pool. The stored pool projection binds
capacityEvidenceRef, capacityEvidenceIssuerRef, capacityEvidenceVersion,
capacityEvidenceDigest, capacityEvidenceIssuedAt,
capacityEvidenceExpiresAt, capacityEvidenceGeneration, and
capacityPolicyVersion. Any stale, expired, revoked, wrong-owner/account/domain,
or inflated-limit envelope is denial evidence only and cannot create, activate,
or widen a pool.

capacity_evidence_version/CapacityPool.capacityEvidenceVersion is exactly that
envelope schema_version literal. capacity_evidence_digest/
CapacityPool.capacityEvidenceDigest is exactly payload_digest, defined as
lowercase sha256:<64-hex> over the RFC 8785 JCS bytes of the eight-field closed
provider_capacity payload above, including policy_version and excluding every
envelope/signature field. The envelope signature covers its entire closed JCS
object with only the top-level signature member omitted. These version/digest
meanings are not interchangeable with the full signed-envelope digest.

capacityGeneration increases on any eligibility-affecting configuration,
capsule, credential, placement, or policy change. denyGeneration is monotonic
and increases before suspend/drain/revoke/rotation barriers; denyState is
allowed or denied. Neither generation may decrement, including after restore.
Increasing maxConcurrency requires new signed provider/terms evidence.
Decreasing it first enters draining/deny so Infinity can reconcile existing
resource leases before fresh eligibility is issued.

### AccountLane

An account lane is the schedulable policy unit exposed to an adapter. Its id is
the ExecutionLaneRef presented to Infinity; Infinity otherwise treats it as
opaque.

Common fields are id, entitlementId, capacityPoolId, adapterKey,
adapterVersion, accessTransport (native_session, api_key, or
workload_identity), status (draft, ready, draining, disabled, or retired),
revision, and timestamps. The state-dependent shape is closed:

- draft forbids requiredIsolationPolicyRef/digest, positive
  executionPolicyEvidenceRef/expiry, and a caller-asserted healthy observation.
- ready requires the authority-derived isolation-policy ref/digest, fresh
  execution-policy evidence/expiry, and a fresh signed health observation.
- draining, disabled, and retired retain last evidence for audit but are
  ineligible; returning disabled to draft archives/clears its positive
  projection rather than treating stale evidence as current.

After activation, entitlementId, capacityPoolId, adapter identity,
accessTransport, and serialization domain are immutable. A change creates a new
draft lane after the old lane is denied/drained; it never reparents live
capacity.

The execution-policy authority derives the lane's required isolation policy
from the signed entitlement/use-case decision and the exact transport/adapter.
accounts:write, owner, and administrator inputs cannot select a weaker policy.
The Machines/capsule attester proves that the measured capsule matches the
required digest; a valid measurement of an unapproved caller-selected policy
does not authorize the lane. Expiry or replacement of this policy evidence
fails closed and advances the capacity-generation/deny barrier before a new
policy can become eligible.

A signed health observation (healthy, degraded, unavailable, or unknown, with
issuer, observedAt, and expiry) is absent in draft and required healthy/fresh
before ready. Unknown, degraded, unavailable, unsigned, or stale fails closed.

Funding and access transport are orthogonal. A subscription-funded entitlement
may expose a node-bound native_session lane or a portable api_key lane; funding
kind never selects transport. A native_session pool has maxConcurrency = 1 in
V1. api_key/workload_identity limits come from explicit provider/terms evidence
and default to one when unknown. Credential generation is fenced separately in
the capability. The Run Authority enforces the pool's serializationKey and
maxConcurrency in resource_leases.

Accounts may answer an eligibility query using typed status, terms, data policy,
health freshness, and capsule readiness. It MUST describe each rejection with a
stable reason code. Eligibility is not a reservation and does not authorize a
run.

AccountLane is independent of sandbox selection. adapterKey names the account/
provider adapter, not an E2B/Daytona runner, and the lane stores no sandbox
RunnerRef. Infinity V1 evaluates exactly E2B and Daytona Cloud behind the
Sandboxes contract; Daytona OSS and any third sandbox provider are out of scope.

### AuthCapsule

An AuthCapsule is a persistent credential-bearing, node-bound native-session
boundary. It is not a task sandbox and not the API-key/workload broker.

Required fields:

- id, accountLaneId, and capacityPoolId
- kind: native_session (the only V1 AuthCapsule kind)
- ownerRef, which MUST equal the ProviderAccount ownerRef
- placementKind: enrolled_node (the only V1 variant)
- placementRef: canonical Machines-issued machine UUID, never a friendly alias
- hardwareKeyThumbprint, nodeGeneration, and placementGeneration
- status: unprovisioned, bootstrapping, ready, degraded, or revoked
- refreshOwnerRef and refreshMode: provider_native or interactive_owner
- authGeneration, incremented on reauthentication/rebootstrap, central
  revocation, placement replacement, or suspected copy
- authStateRevision, monotonically incremented for in-place native state refresh
- isolationPolicyRef and isolationPolicyDigest
- revision and timestamps

attestationRef, attestationIssuerRef, attestationMeasurementDigest, attestedAt,
attestationExpiresAt, and lastHealthAt are required before ready. The signed
attestation binds capsule id, Machines-issued machine UUID, node generation,
hardware-key thumbprint, placement generation, isolation-policy digest, capsule
build/measurement, authGeneration, authStateRevision, nonce, and time. A machine
reimage, hardware-key rotation, or placement change requires a new generation
and attestation.
Replaying evidence for another capsule, node, placement, generation, or policy
is invalid.

accountLaneId, capacityPoolId, ownerRef, and placement identity are immutable.
One partial unique constraint permits at most one non-revoked native capsule
per capacityPoolId. Replacement first denies/drains the pool, proves old native
provider-session revocation and local erase, records the tombstone, and only
then allows fresh login/bootstrap on the replacement node.

Central native revocation atomically advances denyGeneration, makes usable
generation N terminal and irretrievable, advances capsule authGeneration, and
creates an equal no-handle CredentialBinding revocation-barrier tombstone at
N+1, even if the node is offline. It never rewrites an issuer-signed N handle
as though it belonged to N+1. Placement/key change, replacement, or evidence of
a possible second copy follows this same barrier. Any successor capsule/binding
begins strictly above the barrier with a fresh equal generation and fresh
node/placement attestation; an old handle, receipt, SlotEligibility, or
capability can never regain validity.

refreshOwnerRef is a derived authority binding, not a caller- or administrator-
selected delegate. For interactive_owner it MUST equal the human
ProviderAccount ownerRef, and every refresh/reauth requires that owner locally
present at the attached CapsuleHost TTY. For provider_native it MUST equal the
deployment-allowlisted, attested CapsuleHost/adapter service principal bound by
signed policy to this capsule id, owner, canonical node id/key, and adapter; it
cannot be a general Accounts writer or broker principal. refreshOwnerRef and
refreshMode are immutable within an authGeneration. Changing either requires
deny/drain, zero live resource leases, explicit owner authorization,
authGeneration increment/rebootstrap, and a fresh attestation before READY.

Exactly one native provider process tree is the state writer. A routine
provider-native refresh keeps authGeneration fixed but CAS-advances
authStateRevision with a signed native-state digest/receipt; Accounts must
record that revision before the capsule returns to READY or serves another
operation. Rebootstrap/credential replacement increments authGeneration and
starts a new authStateRevision lineage. A central broker never refreshes native
capsule state; broker_serialized applies only to brokered credential operations.

The canonical Machines record must explicitly allow capsule capacity and must
not be operator_only, recovery_sensitive, quarantined, or stale. Friendly
aliases never satisfy placement policy; station01 remains operator-only under
the controlling rollout.

Busy is not a capsule lifecycle state; Infinity derives it from resource_leases.
Revoked is terminal. A ready capsule becomes ineligible when its attestation,
health, terms decision, credential binding, or parent record is stale,
unavailable, suspended, expired, or revoked.

CapsuleHost runtime substates do not create a competing Accounts state machine.
Host LOGIN_PENDING and REAUTH_PENDING project to bootstrapping; OFFLINE,
QUARANTINED, and AUTH_STATE_UNKNOWN project to degraded. Host QUIESCING is
represented by the lane/pool draining-denied barrier, not a new capsule status.
Once a central revoke request commits its deny/revocation barrier, Accounts
immediately records the capsule terminal revoked and its tombstone even when an
offline host remains locally REVOKE_PENDING. That host substate and later erase
receipt are external cleanup evidence; they can never reproject terminal
revoked to degraded/ready or delay the central tombstone. An unexpected
REVOKE_PENDING report without the matching operation/barrier fails closed as
degraded/quarantined but cannot itself assert successful central revocation.
Host ACTIVE is only an observed Infinity resource-lease condition. Eligibility
requires host READY, Accounts capsule/lane ready, and fresh evidence; every
other host substate has zero capacity.

A capsule MUST NOT contain a repository checkout, task workspace, task shell,
host-home mount, Docker socket, Git write credential, database credential, or
arbitrary agent hook. Task code never executes in the capsule. The capsule
exposes only an allowlisted provider channel and narrow tool RPC to the task
sandbox.

AuthCapsule/native_session is node-bound to canonical machine UUID, hardware/node key, node
generation, placement generation, and native protected state; it is never
copied or treated as portable. Brokered API-key access is explicitly not an
AuthCapsule. Its material remains in the trusted broker; portability means a
per-run, exact-operation, sender-constrained proxy channel may serve a sandbox
while the long-lived key never does. The capability is bound to a
non-exportable workload/transport key and Infinity attempt/resource lease; it
is not a bearer token exposed in guest environment, files, argv, logs, or tool
responses. workload_identity follows the same broker/capability rule and is not
a capsule.

The production topology uses the central self-hosted authority plus enrolled
outbound-only infinity-node/CapsuleHost processes. A node authenticates its
canonical machine identity and hardware/node key over outbound TLS, pulls only
signed typed fixed-handler work, and reports evidence. Accounts/Infinity never
opens an inbound node connection. SSH, Tailscale, Mosh, prompt paste, and a
generic remote shell are not task admission, capsule invocation, refresh,
attach, or recovery paths. Operator-only machines run no capsule daemon.

On an AuthCapsule host, any Codewith component is strict fixed-handler/
remote-tool only: no local workspace, shell, hooks, inherited environment, or
task code. This restriction is not applied to Codewith inside the disposable
task sandbox; sandbox Codewith remains fully functional inside the Sandboxes
resource/network/capability policy and has no capsule credential access.

### CredentialBinding

A CredentialBinding maps one lane access target and purpose to opaque resolver
state.

Required fields:

- id, accountLaneId, and capacityPoolId
- authCapsuleId only for capsule_local_native; forbidden for brokered_secret and
  workload_identity
- issuer-signed credentialFamilyId, stable across handle remint/rotation for the
  same upstream credential/quota family
- purpose: provider_session, api_key, or workload_identity
- resolver: brokered_secret, workload_identity, or capsule_local_native
- an issuer-minted credentialHandle, stored server-side only and required for
  pending/active/retiring; forbidden for revoked
- credentialGeneration
- authStateRevision for capsule_local_native only
- refreshMode: broker_serialized for brokered_secret/workload_identity;
  forbidden for capsule_local_native, whose mode lives on AuthCapsule
- status: pending, active, retiring, or revoked
- for revoked, a closed terminal union: retired_handle_generation requires a
  keyed credentialHandleAuditDigest plus revocationBarrierReceiptDigest;
  revocation_barrier requires lastUsableCredentialGeneration plus
  revocationBarrierReceiptDigest and forbids a handle digest because no handle
  ever existed; both variants require terminalKind and revokedAt
- policyDigest
- createdAt, rotatedAt, and expiresAt when known

credentialHandle is not a caller-supplied vault path, ARN, role name, file path,
or provider token. It is an opaque, signed handle minted by the configured
Secrets broker, workload-identity broker, or attested capsule agent. The handle
is bound to owner, provider account, capacity pool/domain, credentialFamilyId,
lane, access-target discriminator, purpose, backend, policy digest, credential
generation, and expiry; native handles also bind the capsule/node. Accounts
validates the configured issuer signature and binding but never dereferences
material.

A credentialHandle is a locator, not a bearer or authorization artifact. The
resolver requires the matching live Infinity capability, sender constraint,
owner/target/purpose, and current Accounts generation/deny check before use.
There is no independent reusable `accounts.handle-resolution.v1` authorization
path in V1. A broker/capsule may resolve a handle only inside the exact operation

maps to one capacityPoolId and one owner/purpose policy installation-wide.
Reminting, rotating, importing, or switching broker backends cannot create a
new serialization domain.

(credentialFamilyId, capacityPoolId, ownerRef, purpose) lineage to its
independent recovery/denial ledger before Accounts creates the first binding.
Accounts mirrors the signed receipt; conflict, timeout, or a stranded append
fails closed and cannot mint a parallel family.

The binding is a discriminated union:

- (accessTransport=native_session, resolver=capsule_local_native,
  purpose=provider_session) requires an authCapsuleId belonging to the same
  lane.
- (accessTransport=api_key, resolver=brokered_secret, purpose=api_key) has no
  authCapsuleId and binds the approved trusted broker.
- (accessTransport=workload_identity, resolver=workload_identity,
  purpose=workload_identity) has no authCapsuleId and binds the approved
  workload-identity broker.

## Evidence issuers and field authority

Eligibility facts are evidence, not ordinary writable metadata. Every evidence
object has a versioned signed envelope containing evidence_type, subject_ref,
issuer_ref, issuer_class, issuer_incarnation, audience, key_id, issued_at,
expires_at, nonce, payload_digest, signature, and source/evidence reference.
Accounts verifies the configured trust root, audience, subject binding,
freshness, nonce, and payload schema before storing it.

Every signed JSON envelope Accounts produces or verifies, including evidence,
SlotEligibility, broker/capsule receipts, and Infinity capabilities, uses RFC
8785 JSON Canonicalization Scheme (JCS) bytes. The parser rejects duplicate
object keys before ordinary JSON parsing, invalid UTF-8/lone surrogates, and
unknown fields in every security-significant closed schema. After schema
validation, the verifier removes exactly the top-level signature member and
JCS-serializes the remaining object; those bytes, and no intermediary
reserialization, are the signature and digest input. Payload digests similarly
cover the JCS bytes of their closed typed payload. Integer counters remain the
canonical decimal strings required by this contract; non-canonical numeric
spellings, leading zeros, unsafe numeric coercion, and overflow are rejected.
Unicode is compared as exact code points with no guessed normalization.
Producers emit canonical bytes, and signer/verifier fixtures MUST compare the
same bytes and digest across at least two independent runtimes.

Accounts-native handles/evidence use issuer_incarnation/catalog_incarnation and
do not invent an Infinity epoch. When a signed receipt is bound to an Infinity
operation it echoes the exact authority_epoch, route_epoch, lease_epoch, and
operation_execution_epoch plus the full route, run/attempt/resource lease,
operation, principal, sender-key, audience/time, target, generation, request,
and recovery-frontier tuple defined for that receipt. A field that is not
applicable is omitted by its versioned schema; it is never renamed, folded into
a generic epoch, or silently set to zero.

The Accounts domain evaluator derives eligibility and accepts a ready/active

Readiness is not a caller-writable boolean. A generic accounts:write credential,

Local mode may co-locate human roles for interactive metadata work, but it still

## State and eligibility invariants

Allowed lifecycle edges are explicit:

| Aggregate | Allowed transitions |
| --- | --- |
| ProviderAccount | pending -> active or revoked; active -> suspended or revoked; suspended -> active or revoked |
| Entitlement | pending -> active or revoked; active -> paused, expired, or revoked; paused -> active, expired, or revoked |
| CapacityPool | pending -> active, denied, or retired; active -> draining, denied, or retired; draining -> active, denied, or retired; denied -> pending or retired |
| AccountLane | draft -> ready, disabled, or retired; ready -> draining, disabled, or retired; draining -> ready, disabled, or retired; disabled -> draft or retired |
| AuthCapsule | unprovisioned -> bootstrapping or revoked; bootstrapping -> ready, degraded, unprovisioned, or revoked; ready -> degraded, bootstrapping, or revoked; degraded -> ready, bootstrapping, or revoked |
| CredentialBinding | pending -> active or revoked; active -> retiring or revoked; retiring -> revoked |
| CredentialOperation | requested -> quiescing or failed_before_dispatch; quiescing -> applying, failed_before_dispatch, or quarantined; failed_before_dispatch -> requested only under the same operation_id/semantic key/source lineage after the external ABORTED_BEFORE_DISPATCH seal, a fresh consumed maintenance grant and execution fence, and epoch exactly +1; applying -> verifying, failed, or quarantined; verifying -> completed, failed, or quarantined. After any DISPATCHED record, every edge to failed is legal only with the configured endpoint's signed failed_no_effect OUTCOME and permanent exact-token tombstone for the highest dispatched epoch and no contrary outcome; otherwise it goes to quarantined. failed -> requested is legal only after the coordinator CAS consumes that same external failed_no_effect, with unchanged operation/semantic/request/target/source-lineage digests, a fresh current execution-fence digest linked to the prior terminal receipt, a fresh consumed one-use maintenance grant, a fresh deterministic epoch token, and epoch exactly +1. quarantined is terminal pending a separately authorized replacement operation. |

CredentialOperation terminality never implies ambiguity-barrier closure.
DISPATCHED-without-OUTCOME, failed_effect, or reconciliation_blocked keeps the
family/serialization domain excluded even after the database row is terminal or
quarantined. Only the exact RESOLVED/COMPENSATED barrier CAS above changes that
exclusion; replacement operation IDs and administrator state edits cannot.

revoked, retired, and expired are terminal. A successful credential rotation
increments generation and atomically retires the prior generation; failure
leaves the prior non-expired generation unchanged or fails closed if it can no
longer be trusted. Every transition requires an actor, reason code, expected
revision, and event.

CapacityPool denied -> pending retains/advances its deny barrier and requires
fresh provider-capacity evidence before active. It never reuses pre-denial
eligibility. Parent suspension/revocation also denies every child pool.
CredentialBinding retiring is permanently ineligible and cannot return active;
it exists for deny-before-destroy receipt completion.

A lane is eligible only when all of the following are true:

1. ProviderAccount is active and its exact owner/subject/realm ownership
   evidence is fresh, unrevoked, and at the current ownershipGeneration.
2. Entitlement is active and effective, and its terms decision is allowed and
   unexpired.
3. CapacityPool is active/allowed, its issuer evidence is fresh, and the lane,
   target, and credentialFamilyId all match its capacityDomainRef.
4. Requested model/operation and data classification are explicitly allowed.
5. AccountLane is ready and its health observation is fresh.
6. For native_session, a linked AuthCapsule is ready, correctly placed, freshly
   attested, owned by the same principal, and has a matching native binding.
7. For api_key/workload_identity, there is no capsule; the lane-level brokered
   CredentialBinding is active, correctly owner/purpose-bound, and unexpired
   when an expiry is known.

Accounts signs items 1 through 7 as non-reservational SlotEligibility with
individual reason codes and observation times. The Infinity Run Authority then
performs admission and atomically issues the account resource lease within
serialization/concurrency, fairness, and budget policy. Accounts MUST NOT
collapse those separate decisions into an isAvailable boolean.

Parent suspension, expiry, revocation, or retirement immediately makes all
descendants ineligible without deleting evidence. V1 exposes no hard-delete
operation; retention-driven physical purge is a separately reviewed
administrative process that preserves a non-secret tombstone and audit chain.
The same transaction changes the affected record revision and derived deny
view; pool-wide denial also advances denyGeneration. Online generation-check
therefore rejects pre-transition record_revision_set even before event/outbox
delivery.

## Infinity resource lease and fenced capability contract

Accounts has no run-lease acquire, renew, steal, retry, cancel, terminal, or
force-unlock method and no account-resource-lease issue/release/tombstone
method. The Accounts CLI and SDK have no mutating lease command.

An unattended capsule/broker action requires an authority-signed capability
bound to:

- capability_schema_version, issuer, authority_epoch, route_lineage_id,
  route_id, route_epoch, key_id, audience, subject, issued_at, not_before,
  capability_expires_at, and capability_id;
- run_id, attempt_id, attempt_lease_id, lease_epoch, resource_lease_id,
  resource_id, resource_lifecycle_generation, and lease_expires_at;
- operation_id (the immutable operation-intent id), operation_digest, and
  operation_execution_epoch and operation_execution_expires_at;
- actor_principal, lease_holder_principal, operation_executor_principal, and
  sender_key_thumbprint;
- account_lane_id, capacity_pool_id, capacity_domain_ref,
  credential_family_id, allowed_channel_class, exact native-capsule or
  broker-binding target,
  slot_eligibility_digest, capacity_generation, deny_generation,
  credential_generation, accounts_revision_set_digest, and native
  auth_state_revision when applicable;
- exact operation, approval_ref, policy_digest, and canonical_request_digest;
- a canonical provider route/destination policy including scheme, normalized
  host, port, operation/path, model, and request-body/argument digest;
- sender-constraint confirmation binding the non-exportable workload/transport
  key, sandbox/attempt identity, and resource lease;
- unique nonce and max_uses with the sole V1 literal `"1"`. V1 is exact-request
  and one-use; there is no streaming/multi-use capability variant.

Those four epoch field names are the canonical Infinity wire names:
authority_epoch, route_epoch, lease_epoch, and operation_execution_epoch.
Aliases such as routeAuthorityEpoch, leaseEpoch, executionEpoch, or a generic
epoch are invalid in capabilities, receipts, persistence, generated schemas,
and fixtures. issuer_incarnation, authority_generation, producer_epoch,
run_lease_id, attempt_lease_epoch, and allocation_generation are rejected.

The canonicalization algorithm and operation enum are versioned parts of the
schema. Arbitrary URLs are not capabilities. Redirects are denied by default;
an allowed redirect must remain inside the signed destination policy. DNS
answers, TLS server name, resolved address class, and egress allowlist are
checked against policy so rebinding cannot widen the destination.

Accounts never persists, logs, traces, emits, or returns a raw capability
presentation, proof-of-possession proof/private key, sender-channel token, or
guest transport credential. Audit records contain only capability_id,
canonical digest, safe issuer/audience ids, nonce-consumption/result metadata,
and receipt digest.

Every privileged operation verifies the signature/key/audience/subject,
authority_epoch, route lineage/id/route_epoch, attempt_lease_id/lease_epoch/
lease_holder_principal, resource_lease_id/resource_id/
resource_lifecycle_generation,
operation_id/digest/operation_execution_epoch/operation_executor_principal,
sender key, request digest, Accounts online generation/deny state, expiry, and
use count. It independently derives actor_principal from the authenticated
transport identity and always requires exact equality with the receipt's
actor_principal. The signed capability itself binds subject and actor; V1 has no
delegation envelope or caller actor override. Subject equality, role-name
matching, or administrator scope never substitutes for the authenticated actor,
holder, executor, sender, or full fence.

does not own ordinary provider/model-call effect outcomes. Its non-rewindable
capability-use ledger and database mirror accept the following exact closed

Accounts verifies the fresh online receipt, live resource/operation fences,
current denial/generations, authenticated principals/sender/channel, exact
request and destination digests, PREPARED model-call anchor, and recovery
frontier in one coherent consume transaction. It conditionally inserts the
one-use tombstone before returning the signed receipt. The external tombstone

Its schema_digest is exactly
`sha256:1238810b9f99b2f197b2701e22d2b8e3a3f09b408287a113f94febe521c1fd6a`.
consume_request_jcs_base64url is the unpadded canonical base64url encoding of
the exact UTF-8 request JCS bytes and consume_request_jcs_sha256 is their
lowercase sha256:<64-hex>. consume_receipt_jcs_base64url is the same encoding of
the exact signed receipt JCS bytes including signature, and
consume_receipt_digest is their lowercase sha256:<64-hex>. Both blobs are
bounded by their closed schemas and the tombstone signature covers the complete
object with only signature omitted. The external use ledger retains those exact
bytes permanently across Accounts restore even after the receipt expires; the
database mirror is not authoritative. An exact consume_request_id plus
byte-identical request/idempotency tuple replay returns the stored receipt bytes
without re-signing. Changed bytes are IDEMPOTENCY_CONFLICT. Concurrent or later
consumption loses. Unavailability, frontier mismatch, a missing tombstone, or a
digest/byte mismatch fails closed.

For an ordinary model/provider call the broker or Run Authority, never Accounts,
owns PREPARED/DISPATCHED/OUTCOME. Ordering is fixed: (1) that owner durably
records PREPARED only under the current OPEN hold_generation and obtains
model_call_anchor_digest; (2) Accounts performs the one-use CAS; (3) the owner
atomically binds consume_receipt_digest/use_id to the same prepared call only if
the identical hold generation remains OPEN; (4) it atomically appends the shared
external DISPATCHED and opens delivery only under another equality check in the
same hold/effect serialization domain. Every delivery dequeue/retry repeats that
check before provider reachability. A crash before consumption resumes the same
prepared anchor; a crash after consumption replays the same consume
request/receipt and cannot create another use. If DRAINING wins after consume
but before binding/dispatch, the owner writes the no-dispatch abort seal for the
same prepared anchor/use; the use stays consumed and no replacement use is
minted. A DISPATCHED call remains hold-blocking until its permitted terminal
closure. Its outcome follows the shared
infinity.effect-journal-outcome/v1 semantics above but uses the broker/Run
Authority's distinct concrete closed model-call outcome schema, never the
Accounts credential-effect outcome schema. Accounts can prove the use was
consumed but never claims provider success/failure. Credential lifecycle
effects remain the only effects journaled by CredentialOperation.

Refresh and credential write-back are serialized under a stable
binding/serialization_key operation mutex that does not change during rotation;
expected credential_generation is a CAS fence, not the lock identity.
On timeout, cancellation, provider loss, key/authority rotation, or authority
unreachability, the broker fails closed. A newer authority_epoch or
issuer-key revocation can never revive an old capability. Verification accepts
a retired signing key only until the maximum capability lifetime ends and only
if the current authority_epoch/key policy still permits it.

Interactive local bootstrap is the only V1 operation that may occur without an
Infinity lease. It requires an attached human owner, runs on the declared
trusted placement, and cannot execute task code. It still requires the distinct
installation-bound local Infinity authority to hold the account resource with
zero leases, effects, and deliveries under the exact hold protocol above; the
local issuer/audience is never accepted by self-hosted production. It also
requires the immutable empty credential-family claim and expected generation
`"0"`. It causes the bound capsule
agent to mint and internally ingest a credential handle, while the owner-facing
result contains only safe binding/attestation ids, generation, and status; it
never returns a reusable token or handle.

## Storage contract

One repository interface and conformance suite define both stores. SQL dialect
files may differ, but domain behavior, constraints, ordering, pagination,
errors, transition rules, and serialized JSON must be equivalent.

Minimum tables:

- accounts_installation
- provider_subject_claims
- provider_accounts
- entitlements
- capacity_pools
- account_lanes
- auth_capsules
- credential_bindings
- credential_operations
- credential_family_claim_mirrors
- capability_use_tombstone_mirrors
- maintenance_hold_receipt_mirrors
- effect_coordination_mirrors
- import_candidates
- evidence_records
- recovery_ledger_receipts
- slot_eligibility_audit
- account_events
- outbox
- idempotency_records
- accounts_schema_migrations

accounts_installation is exactly one deployment-owned row. It fixes
deploymentMode and identityRealm/organizationRef, records the expected
schema/build/configuration attestation, and mirrors (but cannot override) the
restore-resistant catalog incarnation plus exact recoveryFrontier sequence/hash
held outside the restorable database.
No request DTO can create or rewrite it. evidence_records stores immutable,
typed, signed, non-secret evidence envelopes and their closed payloads; it is
issuer/audience/subject/version indexed and never stores credential handles,
capability presentations, device codes, or provider credential material.
provider_subject_claims is an append-only/tombstoned all-time uniqueness map;
its primary/unique key is (providerKey, providerSubjectRef), and immutable
ownerRef/providerAccountId lineage prevents reuse after terminal state or
physical retention purge. It mirrors a claim already conditionally appended to
the external recovery ledger; the restorable table alone never proves all-time
uniqueness. import_candidates stores only redacted, checksummed,
non-authoritative metadata and lifecycle/audit state. Its domain/family hints
can never be joined or copied as authority; configured verifiers/brokers must
independently derive and atomically deduplicate/mint authoritative
CapacityPool/CredentialBinding rows. recovery_ledger_receipts stores only the
signed non-secret frontier sequence/hash and replay receipts needed to prove
gap-free reconciliation; it cannot grant a claim or eligibility.
slot_eligibility_audit stores safe ids/digests/decision reasons only, not the
raw signed presentation.
The four `*_mirrors` tables store only verified record/digest/frontier mirrors;
their non-rewindable external ledgers remain authoritative. A database row can
never clear a hold/barrier, recreate missing evidence bytes, reset a use, or
authorize dispatch after restore.

Portable representation is UUIDv7 text plus RFC3339 UTC text and canonical JSON
in SQLite, and uuid plus timestamptz and jsonb in Postgres. Revisions and all
generation counters are non-negative signed-64-bit database integers with
maximum 9223372036854775807, but their JSON/wire/signature representation is a
canonical base-10 decimal string with no sign or leading zero. TypeScript uses
an opaque decimal-string type or bigint internally and MUST NOT parse/compare
these values as Number. Exhaustion fails closed rather than wrapping. Domain
codecs normalize both stores to identical wire values; evidence issued/expiry
time comes from the database clock, not a caller.

Field ranges are closed rather than inferred from that storage type. Zero is
permitted only for an initial aggregate revision, Accounts capacity_generation,
deny_generation, auth_generation, auth_state_revision, credential_generation,
the recovery-frontier genesis sequence, and use_count before the first use
(plus an explicitly optional
zero-valued bounded policy quantity whose schema says so). maxConcurrency,
ownership_generation, Machines node_generation/placement_generation, Infinity
authority_epoch/route_epoch/lease_epoch/operation_execution_epoch,
resource_lifecycle_generation, and every post-genesis execution/recovery
sequence are strictly positive. max_uses is also strictly positive; use_count is
non-negative, must not exceed max_uses, and both are canonical signed-64-bit
decimal strings on the wire (negative, fractional, signed, leading-zero, and
overflow encodings are invalid). Positive authorization additionally requires
use_count < max_uses; equality is the exhausted negative case with
USE_LIMIT_REACHED. V1 max_uses is exactly `"1"`; use_count is exactly `"0"`
before consumption or `"1"` after it. Any other value requires a new protocol
version. A not-applicable counter is omitted, never zero.

All foreign keys use ON DELETE RESTRICT. Lifecycle transitions use status, not
cascading deletion. Authorization-relevant values are typed columns or
validated typed JSON. Adapter metadata is size-bounded, schema-versioned, and
cannot affect authorization.

Constraints/indexes enforce the immutable all-time provider-subject claim and
owner lineage, unique provider capacityDomainRef/serializationKey, one pool per credentialFamilyId,
same-owner/pool lineage, transport/resolver/purpose discriminator, native
current-binding or newest-revocation-barrier credentialGeneration/
authGeneration equality, revoked-handle absence and terminal-kind constraints,
one active native capsule/binding per pool/purpose, idempotency scope, and monotonic revision/
capacity/deny/auth_generation/auth_state_revision/credential generations. A
database constraint is preferred; any cross-table rule enforced in the domain
layer must have transaction-race tests in both dialects.

Each mutation transaction atomically:

1. validates actor, ownership, expected revision, transition, and parent state;
2. updates the aggregate and revision;
3. appends a redacted immutable event;
4. writes any outbox intent;
5. commits or changes nothing.

- An Accounts component embedded in Infinity uses a dedicated accounts_v1

### Restore and rollback boundary

Every supported restore/import first advances catalogIncarnation in a
non-rewindable, non-secret recovery high-water ledger outside the restorable
database and sets installation recoveryHold before opening any write or
eligibility route. The ledger is deny/fence authority only: it can never grant
eligibility. The same external recovery system preserves the immutable random
effect_namespace_id; catalog/issuer rotation never changes it. With atomic
conditional append it preserves provider-subject
claims, (providerKey, capacityDomainRef) to serializationKey claims,
credentialFamilyId to pool/owner/purpose claims, native revocation barriers,
terminal tombstone digests, and the maximum observed ownership, capacity, deny,
node, placement, auth, auth-state, and credential generations. A
claim/high-water entry is written before the corresponding positive database
transition; if the database step fails, the stranded ledger entry remains
conservatively claimed/denied until reconciled rather than becoming reusable.
Its ordered sequence plus hash-chain root defines recoveryFrontier.

Self-hosted recovery MUST reconcile this ledger or remain offline. A local
restore lacking its matching recovery ledger creates a new installation/issuer
identity and cannot resume, import, or validate any old claim, handle, capsule,
evidence, or tombstone as authoritative. catalogIncarnation alone is not a
substitute for replaying lost uniqueness and generation history.

Under recoveryHold, one locked recovery transaction sequence:

1. rotates the Accounts issuer/catalog incarnation so every prior
   SlotEligibility is invalid;
2. replays missing provider_subject_claims, domain/serialization claims, and
   credential-family/bootstrap/pool/owner claims, native revocation barriers, and
   terminal tombstones from the external ledger before allowing creates, and
   gap-free replays the stable effect namespace plus every signed CLAIMED,
   PREPARED, ABORTED_BEFORE_DISPATCH, DISPATCHED, OUTCOME, ambiguity-barrier,
   evidence-blob, and key-history record before any credential operation may
   prepare or dispatch; it also verifies the current Infinity maintenance-hold
   generation/frontiers, which remain fail-closed across Accounts restore;
3. moves active/draining CapacityPools to denied; moves ready/draining lanes to
   disabled; moves ready/bootstrapping capsules to degraded; and preserves
   pending/draft/unprovisioned/disabled/degraded states and every terminal
   retired/revoked/expired row exactly as terminal;
4. leaves every CredentialBinding lifecycle status unchanged but makes all
   nonterminal bindings unusable through recoveryHold. Broker/capsule proof may
   retain a verified binding at its same status or drive an allowed transition
   to revoked; it never back-transitions active/retiring/revoked to pending and
   never rewrites a terminal retired-handle or revocation-barrier row;
5. revalidates ownership, terms, execution policy, capacity, node/placement,
   capsule attestation, broker denial, and credential-family evidence before
   clearing the hold.

Recovery compares every monotonic high-water value, including
ownershipGeneration, capacityGeneration, denyGeneration, nodeGeneration,
placementGeneration, authGeneration, authStateRevision, and
credentialGeneration. None may decrement. A restored lower native
authGeneration/credentialGeneration pair, a pair that is unequal, a missing
revocation_barrier, or a lower authStateRevision is quarantined; recovery
revokes the old signed generation at its original value and creates/validates a
no-handle barrier strictly above the external high-water under the normal
deny/receipt protocol. It never edits a handle to claim a new generation.
Fresh Machines and CapsuleHost evidence is required for node/placement/auth
high-waters. The same rule applies to brokered generations and all-time
provider/domain claims.

The service refuses normal readiness while recoveryHold is set or database,
deployment, external-ledger, broker, Machines, or capsule high-waters disagree.
Clearing it requires a signed recovery receipt binding catalogIncarnation, the
gap-free external recoveryFrontier sequence/hash root, the database replayed
frontier, and the broker/Machines/CapsuleHost frontier receipts; every
irreversible lineage must be present through that exact frontier. A PITR from
before a subject/domain/family/barrier creation can therefore neither mint a
second serializationKey nor forget a deny/tombstone barrier.
Raw file/database rollback outside the supported recovery command is not a
valid operational mode; doctor/readiness detects any mismatch and fails closed.

## HTTP and SDK contract

The existing published HTTP /v1 routes already mean profile/current/tool CRUD.
They cannot be silently redefined or safely cohosted with capacity. In
particular, shared custom ToolDef environment/launch/permission data creates a
configuration-to-local-process path that does not belong near trusted capacity.

The new domain schema is accounts.capacity.v1. A standalone deployment uses a
clean capacity origin and /v1. An Infinity modular-monolith deployment mounts
the same public package contract under an unambiguous Accounts route/module and
package-owned database schema; it need not add a network service or container.
In either topology, the capacity issuer/audience, auth scopes, build graph, and
schema ownership are distinct from legacy. No V1 target may mount, import,
query, or execute legacy profile/current/tool routes or data.

The explicit legacy cutover is:

1. Keep any still-required local apply/launch/switch behavior in the existing
   quarantined legacy binary, outside the V1 dependency graph and process.
2. Inventory consumers of the existing self-hosted profile API and issue a
   separately audienced capacity endpoint/credential.
3. Disable self-hosted custom ToolDef propagation and freeze the old service
   read-only on its separate origin; never run its process or image beside the
   capacity service.
4. Export only reviewed metadata, import it through the pending-candidate flow,
   record a cutover watermark, and switch each consumer without dual-write.
5. Retire the old service after the read-only compatibility window.

Legacy static keys are cryptographically/audience-isolated and are rejected by
the capacity /v1 and all /internal routes. Capacity credentials are likewise
rejected by the legacy origin.

## CLI contract

The clean CLI is noun-namespaced so existing profile commands remain
unambiguous:

~~~text
accounts provider-account add|list|show|update|status
accounts entitlement add|list|show|update|status|evidence
accounts capacity-pool list|show|evidence
accounts lane add|list|show|update|status|health-evidence
accounts capsule add|list|show|status|bootstrap|reauthenticate|attestation|revoke|doctor
accounts credential-binding list|show
accounts credential-operation request|status|rotate|revoke
accounts capacity eligible
accounts export --metadata-only
accounts import --metadata-only --dry-run
accounts migrate
accounts doctor
accounts status
~~~

There is no public run/resource-lease issue/renew/release/force command.
capacity eligible is a non-reservational diagnostic; its local output is not
accepted by Infinity.

evidence, health-evidence, and attestation only ingest a signed envelope from
the separately authorized issuer; they do not accept a caller-selected
allowed/healthy/ready value. Public credential-operation request/rotate accepts
only brokered_secret or workload_identity bindings and invokes only their
configured broker; capsule_local_native is rejected before an operation intent
or provider interaction exists. Native generation-changing reauthentication is
available only through the attached capsule ceremony above. Routine
provider_native in-place refresh is a separate fixed-handler internal operation
with an exact live capability and safe signed receipt, not a public rotate
method. Public revoke may establish the native deny/generation/tombstone
barrier and queue fixed cleanup, including while the host is offline, but it
can never start login/reauthentication or generate a device code. No flow
accepts a caller-provided vault path, ARN, role, local path, or credential
value.

Every non-ceremony command supports --json with a versioned envelope,
deterministic fields, and no ANSI or prompt. Normal output and JSON use the same
redactor. Mutation commands print aggregate id, revision, event id, and result
only. They never print credentialHandle or a vault/role/path locator; broker
diagnostics show only binding id, resolver class, generation, status, and safe
evidence ids.

Exit codes are stable: 0 success, 2 usage/validation, 3 not found, 4 conflict or
stale revision, 5 unauthorized/forbidden, 6 dependency unavailable, and 7
policy/terms/capsule denial.

- HASNA_ACCOUNTS_DEPLOYMENT=local or self_hosted

- HASNA_ACCOUNTS_CAPACITY_API_URL for self_hosted only
- HASNA_ACCOUNTS_CAPACITY_AUTH_REF for a separately audienced, Secrets-managed
  capacity client credential reference

may be supported temporarily by the legacy client, but it is not part of this

capsule bootstrap/reauthenticate is a sensitive owner ceremony. The CLI refuses

attached CLI TTY, which the CLI then hands directly to the CapsuleHost console.
A remotely created intent alone can never trigger provider interaction.
CapsuleHost—not the Accounts API/CLI event path—renders any provider device URL
or code and never persists it. Device URL/code, cookies, and results are absent
from API responses, JSON, events, logs, traces, shell history, and support
bundles.

The existing add/use/apply/env/launch/run/supervisor/switch/tool commands remain
only in the quarantined legacy binary during cutover. They are not linked or
exported through any V1 CLI/SDK/server target and are prohibited in an Infinity
worker, capsule, broker, or control-plane process. Dangerous permission presets
are not part of Accounts V1.

An MCP adapter, if retained, is a read-only thin projection. It has no capsule
bootstrap, credential ceremony/mutation, run/resource-lease operation, or
production SlotEligibility minting. It MUST NOT expose legacy process-launch or
dangerous-permission operations.

## Security invariants

1. Accounts stores and returns references, never credential material.
2. Subscription capacity is bound to its human owner. No pooling,
   impersonation, relaying, resale, or model-API exposure is allowed.
3. Unknown or stale terms, data policy, health, attestation, credential
   generation, or authority state fails closed.
4. Infinity Run Authority is the only Infinity attempt-lease authority for a run.
   It also owns account-slot resource leases. SlotEligibility is
   non-reservational and insufficient without a live Infinity capability.
5. Native material resolves only inside its attested node-bound capsule;
   Secrets/workload material resolves only inside a trusted broker action with
   a live exact-operation capability.
6. Untrusted task sandboxes receive no subscription session, API key, AWS
   credential, guest-visible provider bearer, Git write credential, database
   credential, vault access, or capsule filesystem.
7. Control-plane and task-workload placements are forbidden for
   credential-bearing capsules.
8. Every mutation is actor-bound, owner-checked, revision-checked,
   idempotent, transactional, audited, and redacted.
9. No authorization decision may depend on untyped metadata, a display label,
   a local path, a process PID, or current/applied profile selection.
10. Local and self_hosted never silently synchronize or fail over to each
    other.
11. Status propagation is fail-closed and evidence-preserving; revocation never
    deletes history.
12. Provider-native refresh is serialized. A stale generation cannot overwrite
    a newer generation.

## Non-goals

- A provider marketplace, subscription product, or outside-user SaaS.
- Daytona OSS, a third V1 sandbox provider, or encoding E2B/Daytona Cloud as
  Accounts domain entities; those two managed providers belong to Sandboxes.
- A general model router or provider abstraction in the Infinity kernel.
- Run scheduling, fairness, retry, budget accounting, or backpressure.
- A Secrets replacement, credential proxy implementation, or raw token API.
- A task sandbox, shell runner, agent supervisor, repository manager, Git
  promoter, or deployment system.
- Automatic provider-terms interpretation or legal approval.
- Same-provider-subject or same-capacity-domain ownership transfer/successor
  lineage in V1.
- Provider billing reconciliation.
- Generic workflows, recurring loops, or OpenLoops replacement.
- Shared homes/worktrees, device-login-per-task, environment-secret injection,
  S3 registry synchronization, or path-based cleanup.
- A self-hosted trusted-cell AuthCapsule placement variant in V1; native
  capsules are enrolled-node-only.
- Treating local profile current/applied state as fleet capacity.
- Automatic migration of credential files, keychain payloads, or API keys.

## Legacy migration contract

Migration is additive and dry-run first:

1. Inventory exact package/source/database versions and freeze a redacted input
   manifest.
2. Run a quarantined data-only importer whose file allowlist is the reviewed
   registry export. It has no profile-directory, Keychain, Secrets, network,
   child-process, shell, or legacy-module access.
3. Import each legacy Profile only as a candidate mapping:
   tool -> provider/adapter hint, identity -> ownerRef candidate, and name ->
   displayLabel.
4. Never copy dir, extraEnv, permissionArgs, launchArgs, credentials.json,
   keychain snapshots, OAuth snapshots, or S3 registry content into V1 rows.
5. Require an operator to confirm the provider-account candidate, owner,
   funding kind, access transport, and placement/broker request, then request
   the independent ownership, capacity-domain, terms, and execution-policy
   authorities. The operator cannot choose their positive facts.
6. Bootstrap or rotate through the configured broker/capsule agent and create a
   new pending CredentialBinding only when it atomically returns an
   owner/purpose-bound signed credentialFamilyId and handle.
7. For native transport, attest the capsule; for brokered transport, attest the
   broker binding. Run parity/security tests and only then mark the lane
   ready.
8. Keep legacy routes and commands read-only/deprecated until all consumers are
   inventoried. Do not dual-write legacy profiles and V1 capacity records.

current and applied selections have no migration meaning. Custom ToolDef data is
untrusted compatibility configuration and cannot become an authorization or
execution policy.

## Required tests and release gates

### Normative conformance case IDs

The fixture manifest, this contract, and the Accounts red-team corrections use
the following stable, omission-sensitive IDs. Every case is required for V1;
none may be skipped or silently renumbered.

- **ACC-001 — explicit deployment mode/no fallback:** local and self_hosted
  selection, contradictions, missing endpoint, stale local data, and ambient
  credentials never cause an implicit mode change or local mutation.
- **ACC-002 — cross-store parity:** the same randomized transition, pagination,
  revision, idempotency, migration, backup, and restore corpus has equivalent
  SQLite/Postgres domain outcomes.
- **ACC-003 — self-hosted authorization/RLS:** missing scope, wrong owner,
  forged actor, cross-owner ID, stale revision, and replay deny without
  existence disclosure.
- **ACC-004 — credential canary non-persistence:** synthetic secret canaries in
  every input/failure are absent from database, backup, events, outbox, logs,
  traces, CLI, and MCP.
- **ACC-005 — lifecycle/evidence denial:** every forbidden transition and stale,
  unknown, denied, or expired terms/health/policy/attestation makes descendants
  ineligible; metadata cannot widen authority.
- **ACC-006 — funding/transport independence:** the full fundingKind x
  accessTransport cross-product preserves distinct native and brokered shapes.
- **ACC-007 — SlotEligibility forgery/freshness/fences:** forged, expired,

  evidence still requires the live Infinity lease and online check.
- **ACC-008 — sole lease authority/concurrency:** Accounts exposes no lease
  table/issuer and concurrent maxConcurrency=1 acquisition admits one Infinity
  resource lease.
- **ACC-009 — stable capacity identity:** rotation, rename, clone, capsule
  replacement, and archive/recreate reuse the serialization key and invalidate
  stale generations without parallel capacity.
- **ACC-010 — crash-safe credential saga/effect ledger:** every power cut,
  reordered outcome, semantic-operation replay, failed_no_effect proof,
  one-use CAS, and revoke/start/write-back race commits at most one effect and
  quarantines ambiguity.
- **ACC-011 — restore-resistant denial:** restore behind a later deny/revocation

  tombstones reconcile first.
- **ACC-012 — node-bound native handle:** copying a handle across node, alias,
  generation, owner, purpose, or policy never resolves.
- **ACC-013 — portable API-key isolation:** a subscription API-key lane creates

  sender-constrained typed RPC.
- **ACC-014 — SDK/CLI/OpenAPI parity:** local/self-hosted golden envelopes, exit
  codes, redaction, noninteractive behavior, and generated OpenAPI agree and
  expose no handle/locator/material.
- **ACC-015 — no SaaS/outside-realm surface:** schema, migrations, exports,

- **ACC-016 — legacy physical isolation:** built reachable artifacts contain no

- **ACC-017 — SQLite filesystem/schema safety:** symlink, owner/mode, WAL/SHM,

- **ACC-018 — Postgres namespace/role safety:** hostile search_path,

- **ACC-019 — exact integer boundaries:** adjacent 2^53 and signed-64 maximum
  counters round-trip identically; leading-zero, negative, overflow, wrap,
  decrement, and alternate encodings reject.
- **ACC-020 — verify-full Postgres TLS:** plaintext/downgrade, no peer
  verification, wrong CA/hostname/SAN, expired/future certificate, and failed
  CA rotation reject.
- **ACC-021 — pooled-connection RLS reset:** two owners interleaved through
  success, exception, rollback, cancellation, and connection reuse cannot

- **ACC-022 — immutable ownership/domain lineage:** concurrent provider-subject
  activation and every owner/FK/transport/domain rewrite path admit exactly one

- **ACC-023 — shared upstream capacity convergence:** sibling entitlements,

- **ACC-026 — local-console ceremony secrecy:** device URL/code creation is

- **ACC-027 — canonical full-fence sink verification:** omitting/altering every

- **ACC-028 — closed native/brokered variants:** every mixed binding and refresh

- **ACC-029 — canonical safe placement:** only enrolled_node with current
