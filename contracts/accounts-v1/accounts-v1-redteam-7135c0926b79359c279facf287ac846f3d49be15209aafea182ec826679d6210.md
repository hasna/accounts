## Verdict

Do not release from the original drafts. The successor removes the second run
lease/fence authority, admits only exact-request one-use capabilities, separates
Accounts-owned use consumption from broker-owned model effects, and gives
credential maintenance a distinct one-use Accounts authority. The following
historical blockers remain the adversarial checklist; each must be proven closed
against the exact successor bytes rather than assumed closed from prose.

The successor also claims to close the later exact preaudit findings, which are
mandatory fresh-review targets:

1. Accounts, not the capsule/broker, atomically consumes the maintenance grant;
   signed PREPARED binds that receipt and sink reachability begins only after the
   external DISPATCHED CAS.
2. One external coordinator atomically CASes a stable semantic-step index across
   signed CLAIMED, PREPARED, ABORTED_BEFORE_DISPATCH, DISPATCHED, and OUTCOME.
   A sealed old epoch can never append after +1 is authorized.
3. A failed_no_effect retry is permitted only after the endpoint atomically
   installs a permanent rejection tombstone for the old epoch token. The next
   epoch uses a distinct deterministic token, so a delayed old request cannot
   race into acceptance.
4. `effect_namespace_id`, unlike catalog/issuer incarnation, survives supported
   restore. Exact signed claim/prepared/abort schemas and an Accounts-derived
   action-to-step map close caller-selected deduplication namespaces.
5. The shared `7ab380...` object is semantics only. Accounts uses its own exact
   concrete credential-effect outcome schema; the model broker uses a different
   concrete model-call envelope.
6. Capability consumption persists the exact request and signed receipt JCS
   bytes in the external tombstone and replays those bytes without re-signing.
7. One closed reason-code registry rejects unknown aliases and reserves
   USE_LIMIT_REACHED for exhausted online receipts.
8. Accounts owns the signed drain barrier; Infinity independently owns one
   linearizable OPEN -> DRAINING -> HELD admission/effect/delivery hold. HELD
   requires zero leases, unresolved effects, and queued deliveries and persists
   until signed reconciliation plus RELEASE; expiry never reopens admission.
9. Immutable source_lineage_digest is separate from the fresh per-epoch
   execution_fence_digest. A successor PREPARED binds its exact prior signed
   abort/failed_no_effect receipt, allowing current receipts/frontiers to
   advance without changing the semantic operation key.
10. Every cross-ledger digest is defined from exact signed JCS bytes with
    transitive equality, every epoch record has a closed identity/fork rule, the
    CAS+append is one physical transaction, and non-rewindable signer-key
    history preserves verification across retirement/restore.
11. Reverse operation-ID uniqueness, closed request/operation digest domains,
    endpoint-incarnation idempotency binding, strict OUTCOME times, and the
    empty bootstrap-family preclaim are explicit.
12. The family/serialization ambiguity barrier spans overlapping model and
    credential effects. Exact evidence bytes are retained for the namespace;
    failed_effect/reconciliation_blocked cannot be bypassed by a new action,
    semantic key, operation ID, or administrator edit.

The preserved implementation checkpoint `8c681cf82307bbc33364b47f4506d647b1e327f0`
remains explicitly **NO-GO**. Independent review found it still pins the old

### B1 — Remove the second Accounts lease/fence authority

**Evidence.** The Accounts draft says the Infinity Run Authority is the only
lease/fence issuer and gives Accounts no acquire/renew/release method
(`accounts-v1-contract-8562d021c86040bbf2f53c3b6f25b26a0897f8113674037ecc386d31921719f0.md`,
Authority boundaries and Lease contract). The capsule
draft instead defines `Accounts acquisition`, an `account_lease_id`, a
`LaneFence(accounts_restore_authority_epoch, lane_generation, slot_sequence)`,
renewal of both fences, an Accounts mutation lease, and Accounts force-fencing
(`auth-capsule-contract.md`, Concurrency-one, Refresh, and Revocation).

**Failure path.** A restore, delayed event, partial renewal, or network partition
can make the two authorities disagree about the slot. Each can then consider a
different holder current. Requiring two fences does not fix split brain; it
creates two schedulers and two recovery epochs.

**Required correction.** Delete Accounts acquisition, `account_lease_id`,
Accounts restore epoch, lane-fence renewal, mutation lease, and force-fence
semantics. The Run Authority must issue the sole resource lease and monotonically
increasing fence, bound to its non-restorable `authority_epoch`, run, attempt,
lane, capsule, exact Accounts revisions/policy digest, credential/capsule
generation, node binding, operation, audience, nonce, and expiry. Accounts may
issue short-lived signed **eligibility evidence** that is explicitly
non-reservational and cannot start work. The host's durable lifecycle lock and
monotonic local session sequence remain independent enforcement, not an Accounts
lease. Revocation must cause the Run Authority to advance the sole fence; failure
to obtain that acknowledgement remains fail-closed/pending.

Also make the subscription serialization domain stable for the provider account
or credential family. The current Accounts draft makes `serializationKey` unique
to a credential generation; rotation would change the mutex key and can admit an
old-generation and new-generation session concurrently.

### B2 — Physically isolate V1 from the legacy credential/process runtime

**Verified legacy attack surface.** In the 0.2.6 bundle:

- `dist/index.js:4902-4918,4924-4938,5037-5134` copies full Claude credential
  payloads, serializes a Keychain secret to a profile JSON snapshot, and restores
  credential state to files/Keychain.
- `dist/server/index.js:329-342,768-790` accepts and persists a shared custom
  `ToolDef` containing arbitrary binary, environment, launch arguments, and
  permission arguments.
- `dist/index.js:5920-5946` copies those RDS-backed tool definitions into a local
  execution cache; `dist/index.js:6487-6491,7429-7432` spawns the selected binary
  with the parent process environment inherited.
- `dist/mcp.js:25322-25397` exposes model-callable profile switching, arbitrary
  extra args/permission selection, supervisor restart, and a returned command
  line.
- `dist/server/index.js:663-669,1037-1046` implements a global registry guarded
  only by broad read/write scopes; repository queries have no owner predicate.

**Failure path.** A compromised legacy write key or legacy MCP/tool path can
place executable configuration in the shared registry, have a client cache it,
and later launch a local process with inherited credentials. The same runtime can
also copy raw provider auth state. Co-hosting `/v1` legacy profile CRUD and `/v2`
capacity on one service/origin/audience leaves that confused-deputy path adjacent
to the new boundary.

**Required correction.** Make capacity V1 a separate build/runtime, service
identity, auth audience, database namespace, and SDK entrypoint that cannot import
legacy profile, custom-tool, child-process, Keychain, environment-export, or
credential-snapshot modules. Keep legacy compatibility local-only in a distinct
binary/package. Do not serve shared mutable custom `ToolDef` records to Infinity
workers. If an HTTP compatibility route must temporarily survive, put it on a
separate origin/audience/process, make it read-only, and deny all Infinity
principals. Remove the legacy mutating MCP tools rather than relying on a prose
prohibition.

Add a build gate proving the capacity bundle has no `child_process`, raw
`process.env` inheritance, Keychain calls, credential snapshot filenames,
arbitrary executable/argv/env fields, or legacy MCP switch tool.

### B3 — Make node binding explicit in the Accounts schema and capability

**Evidence.** Accounts currently records a caller-supplied-looking
`placementRef` plus an attestation reference/digest, but its required fields and
fenced capability do not explicitly carry the Machines-issued node generation or
hardware/workload key. The capsule draft correctly defines the stronger tuple
`(canonical_node_id, node_generation, node_key_thumbprint, capsule_generation)`.

**Failure path.** A cloned disk, reimaged host, restored database, rotated node
key, or duplicate friendly alias can retain the same placement string and replay
old eligibility/capability material on different hardware.

**Required correction.** Accounts must normatively reference one placement
binding containing the canonical node/cell ID, control-issued monotonic node or
workload generation, non-exportable key/workload-identity thumbprint, capsule
generation, measured build/policy digest, attestation issuer, challenge nonce,
and expiry. Bind that tuple into the credential binding, eligibility evidence,
Run Authority capability, mTLS identity, host receipt, and Secrets/broker release.
Reimage, restore, key rotation/loss, hardware replacement, placement change, or
possible credential copy advances the generation and tombstones the prior tuple.
Friendly aliases and a software-key fallback must be rejected. Reconcile the
Accounts lifecycle enum with the capsule host's `OFFLINE`, `QUIESCING`,
`REAUTH_REQUIRED`, `REVOKE_PENDING`, and `QUARANTINED` states; if those are
host-internal states, define a single fail-closed projection instead of two
competing state machines.

### B4 — Do not force native sessions through a Secrets locator model

**Evidence.** Accounts requires every `CredentialBinding` to contain a
server-side `secretRef` or `roleRef` and exposes an internal
`accounts:credentials:refs:read` path. The native capsule contract explicitly
keeps native session state only in the bound Mac Keychain/APFS volume and forbids
copying it to AWS or Secrets.

**Failure path.** Implementers must either copy native state into Secrets, store a
local path/Keychain locator in RDS, or invent a fake secret reference. Each option
breaks the node-bound design or creates a credential-locator oracle. A normal
secret path/role ARN also leaks authority topology into Accounts backups and
expands a broker compromise.

**Required correction.** Add a `capsule_local` binding variant that stores only a
non-routable opaque host-state handle plus node/capsule generation and safe auth
state revision—never a path, Keychain label, fingerprint, or resolvable locator.
For brokered secrets/workload identity, store only a Secrets/broker-issued opaque
binding handle cryptographically bound to owner, capsule, purpose, and policy;
Secrets owns the handle-to-locator mapping. Remove the Accounts endpoint/scope
that returns a vault path or role reference. Use allowlist serializers rather
than post-hoc redaction.

The metadata export/import path must exclude active credential bindings,
placement/node bindings, attestations, lease observations, and live capsule
state. An imported lane starts draft/unprovisioned and must be rebound and
reattested. “Opaque references” are not automatically safe or portable.

### B5 — Specify a crash-safe refresh/rotation/revoke protocol

**Evidence.** The Accounts draft says a successful rotation “atomically” retires
the previous generation and serializes refresh per credential generation. That
cannot be one transaction across Accounts Postgres, Secrets/provider state, and
the capsule host. The capsule draft uses a different model: in-place native
refresh advances `auth_state_revision`, while reauthentication advances
`capsule_generation`. It also currently asks Accounts to grant a mutation lease,
which reintroduces B1.

**Failure path.** Power loss after writing a new provider/Secrets value but before
the Accounts CAS can orphan a live credential. A stale receipt can later activate
it. Locking “per generation” changes the lock key during rotation. Concurrent
revoke and refresh can allow refresh completion to reactivate a centrally revoked
session, and a restored Accounts database can point at an older still-valid
secret.

**Required correction.** Freeze one durable protocol before implementation:

1. use a stable mutex domain per provider account/capsule, not per generation;
2. distinguish `capsuleGeneration` (new/copyable login), native
   `authStateRevision` (in-place single-writer refresh), brokered `secretVersion`,
   and a monotonic `revocationEpoch`;
3. persist an idempotent operation ID and expected revisions; create any new
   broker value as pending, validate a signed host/broker receipt, CAS the
   Accounts state, activate exactly one version, then retire the old version;
4. on any ambiguous/crash state, quarantine or resume the same operation—never
   restore a stale refresh token or mint a new operation;
5. revoke makes capacity centrally ineligible and advances the revocation epoch
   before waiting for host/provider erasure, causes the Run Authority to fence
   the active lease, disables the route, and tombstones the broker/host binding;
   refresh/write-back checks the epoch both before work and at commit;
6. keep provider revocation, local erasure, and central scheduling denial as
   separate evidence fields.

Power-cut every transition, reorder/duplicate receipts, race refresh with
start/cancel/revoke, and restore each database in the adversarial suite.

### B6 — Harden the local/RDS authority split and temporary shared-RDS use

The explicit `local | self_hosted` selector and no-fallback rule are good. The
remaining storage details are insufficient if the temporary deployment shares
an existing RDS instance.

**Required correction.** Use a dedicated database or locked schema and dedicated
runtime/migrator roles, fixed safe `search_path`, namespaced migration ledger,
outbox and idempotency tables, an advisory migration lock, runtime denial of DDL
and other schemas, TLS hostname/CA verification (`verify-full` semantics), and
separate backup/restore tests. Never reuse the legacy global `accounts`,
`current_selections`, `custom_tools`, or API-key authority. Queries must constrain
the authenticated owner as well as scope; the authenticated principal, not a
request/SDK `actorRef`, is authoritative in self-hosted mode.

For SQLite, verify owner-only directory/database/WAL/SHM permissions after each
creation, symlink refusal, transaction behavior, and schema high-water handling.
The parity suite must cover semantic results, not claim that local caller identity
provides the same security boundary as self-hosted authentication.

### B7 — Turn “not SaaS” from prose into an enforced invariant

**Evidence.** The draft excludes `cloud` mode and outside-user SaaS, but it still
proposes a general owner/admin HTTP catalog and, currently, co-hosting with the
legacy cloud-named service. No principal-issuer/organization admission rule or
network exposure rule makes the Hasna-only boundary machine-checkable.

**Required correction.** Pin the self-hosted API issuer, audience, and allowed
OpenIdentities namespace to Hasna-controlled principals; reject external owner
namespaces even for ordinary admin calls. Deploy on a private authenticated
origin with no public signup, tenant/org administration, customer billing,
API-key minting, permissive CORS, browser-cookie auth, or public discovery path.
Add negative schema/route/config tests for `cloud`, `remote` as a mode,
tenant/signup/billing surfaces, automatic URL/key mode selection, and external
owners. A break-glass administrator may repair metadata but may not convert the
service into an outside-user capacity pool.

MCP should be a separately configured read-only projection for agents. Human
bootstrap, credential binding/rotation, revoke, and any device authorization
code must not appear as model-callable MCP tools. Device login URL/code output is
a sensitive, one-use owner ceremony: restrict it to the attached local console,
never JSON/MCP/logs/events.

### B8 — Correct the provenance inventory before migration

The draft says the globally installed package is 0.1.15. Current filesystem
evidence instead shows the PATH-preferred local shim targets a self-host package
whose package metadata is 0.1.33, while the Bun-global package metadata is 0.2.6;
the compiled CLI fallback constant is 0.1.31 and the MCP server declares 0.1.21.
This is stronger evidence of version drift, but the exact 0.1.15 claim is not
reproducible from the inspected state.

Before migration, generate a redacted manifest containing resolved executable,
package version, embedded build/MCP version, artifact digest, source commit, DB
schema version, and service image digest. Refuse migration or compatibility
startup when these disagree. No legacy profile or credential import is safe
until the exact source/artifact pair is identified.

1. Reconciled Accounts/AuthCapsule schemas with one Run Authority lease/fence

4. Crash/replay/race tests for refresh, rotation, revoke, and late write-back.
5. SQLite/Postgres conformance plus shared-RDS role/schema isolation and restore

6. Secret-canary scans of request fields, DB/backups, events/outbox, logs,
   CLI/MCP output, host process metadata, and checkpoints—with allowlist
   serialization as the primary control.
7. Negative no-SaaS route, identity, configuration, and network-exposure tests.
8. A corrected, digest-pinned legacy provenance manifest.

Until all eight are evidenced, the safe scope is metadata schema prototyping and
the API/IAM golden path only. Unattended subscription capacity remains NO-GO.
